# WWW: выбор архивного действия — 2026-11-16

## Наблюдение и границы диагноза

В переданном владельцем логе `www-tool-probe-3-001` все три вопроса закончились
без поиска: два `completed`, один `abstained`, ноль runtime errors. Вопросы о
наличии ранней архивной фотографии и источнике архивного снимка также не вызвали

хотя архив не был проверен. Полный текст второго ответа в логе отсутствует;
один `decision=supported` не позволяет проверить его фактическую корректность.

В коде обнаружено, что `archival_qa/supported` допускал ссылки только на локальные
фото. Это конкретный дефект проверки происхождения свидетельств. Повторяемый
шаблон final в начальном запросе и после retrieval мог подталкивать модель
к немедленному ответу; это гипотеза о причине поведения, не доказанный механизм.

### Уточнение по реальному probe-002

Владелец передал шесть исходных ответов Qwen: по две попытки на вопрос.
Для обоих архивных вопросов модель явно выбрала `action=retrieve`, для
локального контроля — `action=answer`. Вызовов поиска всё равно не произошло:
обработчик ожидал `type`, а модель вернула `stage/action`, опустила необязательный
`observation_id` и добавила пояснение `reason` к локальному выбору. Это ошибка
совместимости обработчика с фактическим JSON, а не свидетельство отказа искать.

Исправление принимает обе однозначные формы, сохраняет исходный parsed JSON
и отдельно записывает `normalized_action` с журналом преобразований. Только
отсутствующий необязательный `observation_id` получает null; действие, запрос
и пояснение не переписываются. Пояснение выбора не становится свидетельством
или GT. Конфликт `type`/`action`, неверный stage, неизвестное действие, лишние
аргументы и отсутствующий query по-прежнему отклоняются с конкретной ошибкой.

В исправлении probe-002 prompt revision оставалась v2: выбор действий соответствует этим
трём диагностическим вопросам. Меняется только формат разбора:
`action_transport_revision=2026-11-16-action-envelope-v1`. Implementation hash
меняется; старые runs и их статусы сохраняются, resume из них не используется.
В поиске query передаётся Jina как текст без переписывания; строки `date:` и
`building_id=` не вводят дополнительные жёсткие фильтры поверх действующей
проверки identity/availability.

### Уточнение по полному реальному probe-003

В диагностическом архиве сохранены три настоящих успешных вызова archive_search:
два для Каменноостровского 61, один для Марата 44; локальный контроль не искал.
Итог старого запуска: 0 completed, 0 abstained, 3 errors, 498.8 секунды.
Выбор инструментов и dispatch работают; ошибки произошли при переходе к final.

- Полный локальный ответ дважды возвращён со `stage="answer"` вместо `type="final"`.
  После замены только транспортного обозначения обе копии проходят проверку
  исходных IDs, временного интервала и common support. Это один вопрос,
  а не два независимых успешных ответа и не проверка фактического описания RGB.
- Три архивных ответа содержат явный `action="answer"` и вложенный черновик
  `response` либо `response_contract`. Обязательных полей final в них нет.
  Такой объект принимается как выбор ответа на этапе choose_action, но сам
  по себе никогда не становится оценочным ответом. Полный final запрашивается
  у модели; даты, IDs, decision и citations обработчик не дописывает.
- У Каменноостровского оба поиска уже израсходованы. Прежний дополнительный
  выбор действия, повтор и генерация отказа закончились timeout в пределах
  прежних 300 секунд. Теперь при исчерпании раундов или числа записей сразу
  выдаётся контракт final, допускающий и ответ, и обоснованный отказ.

Содержательные ограничения сохраняются. Четыре показанные записи 2015/2024
не доказывают отсутствие более ранних снимков во всём архиве. Для Марата
вложенный черновик ссылается на действительно показанную запись с годом 1929,
но `1929-01-01` — нижняя граница годового интервала, не установленный день съёмки.
Эти формулировки нельзя автоматически объявить верными по совпадению evidence_id.
Query остаётся семантическим текстом; `date:`/`date_range=` не являются фильтрами.
Теперь это прямо указано в публичном управляющем сообщении.

## Изменение протокола

Текущая revision: `2026-11-16-final-handoff-v3`;
`action_transport_revision=2026-11-16-action-final-envelope-v2`.

- В C сначала идёт отдельный запрос выбора действия: `retrieve`, `answer` или
  `abstain`. До этого выбора шаблон финального ответа не передаётся. После
  поиска агент может выбрать ещё один поиск в пределах прежних лимитов.
  Уже полный final также может завершить этот этап, только после всех прежних
  проверок свидетельств, дат, принадлежности координат и типа задачи.
- `answer` переключает на формирование final; `abstain` также формирует final,
  но только с `insufficient_data/incomparable`. Без поиска разрешены и локальный
  ответ, и отказ. Автоматического dispatch по типу вопроса нет.
- Для `archival_qa` выбор `answer` без показанных архивных записей отклоняется;
  агент может выбрать поиск либо отказ. В финальном `supported` для всех A/B/C
  обязательна хотя бы одна ссылка на действительно показанную архивную запись.
  Наличие такой ссылки проверяет происхождение, а не истинность всего текста.
- Контекст явно различает `not_searched`, `no_matches`, `records_returned` и
  `unavailable`. Пустая выдача относится к запросу и фильтрам, а не доказывает
  отсутствие свидетельств во всём архиве. Семантическая проверка утверждений
  об отсутствии записей по-прежнему требует factual review.
- Все запросы выбора, повторные попытки и финальная генерация оплачиваются из
  прежних лимитов Qwen, токенов, изображений и времени. Jina учитывается как
  прежде. После исчерпания лимита поиска отдельный запрос выбора пропускается;
  следующий запрос требует final, включая допустимый отказ. Это не увеличивает
  лимиты и не выбирает содержательный ответ за модель.
- В терминале видны этап выбора, выбранное действие и реальный вызов инструмента.
  Переход к final после исчерпания поиска также выводится сразу. `calls`,
  `messages`, `reply-*`, `exposure`, `costs` и `events.jsonl` сохраняются.
- Полный `stage="answer"` принимается как транспортная форма final; его поля
  не переписываются. Неоднозначные оболочки и неполные черновики отклоняются.
  В reply-* отдельно сохраняется `normalized_final`; исходный текст остаётся
  в calls/messages, исходный parsed объект — в reply-* и final_raw.

Общие инструкции и начальные фото A/B/C одинаковы. Финальный контракт выдаётся
на этапе ответа. Веса, retrieval, фильтры, вопросы, разметка, UI и human approvals
не меняются. Новый execution contract запрещает resume старых запусков.
Для итогового сравнения нужны A/B/C одной новой revision; старые ответы нельзя
смешивать с обновлённым C как с неизменным экспериментом.
