# Сочетания методов: исходные пороги и общий бюджет FPR

## Два разных сравнения

Ночной отчёт сохраняет исходные рабочие точки моделей и показывает PREVIOUS,
EARLIEST, HISTORY, а также AND и OR между PREVIOUS и историческим сигналом.
AND оставляет подтверждённые обоими компонентами пиксели; OR сохраняет тревогу
любого компонента. Каждая комбинация сравнивается с каждым компонентом отдельно
на одинаковых парах и пикселях, с теми же срезами split, обучающей принадлежности
фасадов и классов. EARLIEST не смешивается с HISTORY: состояние относительно
первого кадра и новое событие имеют разные цели.

При исходных порогах OR обычно увеличивает и полноту, и FPR. Прибавка F1 сама
по себе не доказывает, что комбинация лучше каждого компонента при том же
допустимом числе ложных тревог. Поэтому отдельно выполняется CPU-анализ
с общим бюджетом **итогового FPR**, а не только FPR дополнительной ветви.

## Калибровка по реальному VAL

Для каждой пары методов сначала фиксируется общая поддержка: одинаковые
пары, известные GT-пиксели и геометрически допустимая область. Пиксели с
неизвестной разметкой не превращаются в отрицательные. Источник — сохранённые
карты реального VAL и их проверяемые метаданные; GPU, обучение, RGB-подготовка
и обновление временной памяти не запускаются.

Один фасад оставляется для оценки. На отрицательных GT-пикселях остальных
фасадов отдельно подбираются пороги одиночного scalar-метода, AND и OR.
Фасады имеют равный вес, внутри фасада — равный вес кадров с известными
отрицательными пикселями. Положительная разметка оставленного фасада не
участвует в выборе порога. Порог применяется как `score > threshold`; одинаковые
оценки не разделяются ради достижения точного процента.

Общий бюджет означает ограничение на калибровочных фасадах. Фактический FPR
оставленного фасада может отличаться от бюджета. Отчёт должен показывать оба
значения, достижимость бюджета и покрытие. Это разведочная LOFO-калибровка
порогов на VAL, а не независимая оценка всей процедуры выбора модели.

## Ограничения бинарных компонентов

AnyChange и GeoSCD здесь предоставляют исходные бинарные маски. Их рабочую точку
нельзя произвольно передвинуть без изменения метода. Такая маска остаётся
фиксированным ориентиром; если её FPR выше бюджета, она явно отмечается как
находящаяся вне ограничения.

Для фиксированной маски `A` и пороговой маски `B(t)`:

- `FPR(A OR B(t)) >= FPR(A)`: FPR исходной маски — нижняя граница OR.
- `FPR(A AND B(t)) <= FPR(A)`: FPR исходной маски — верхняя граница AND.

Если нижняя граница OR выше бюджета, соответствующий fold недостижим. Он не
получает фиктивную пустую маску и не исчезает из отчёта о покрытии. Сравнение
успешных folds повторно считает оба компонента именно на этих folds. Частичное
покрытие не позволяет выдавать результат за оценку всей исходной выборки.

Одинаковый бюджет не гарантирует одинаковый достигнутый FPR: возможны связанные
оценки, дискретные маски и перенос между фасадами. Заявлять преимущество при
точно равном FPR по таким строкам без проверки фактических значений нельзя.

## Интерпретация и следующие данные

P/R/F1/IoU усредняются по положительным GT-кадрам внутри фасада, затем по
фасадам. FPR использует все известные отрицательные GT-пиксели с тем же порядком
усреднения. Классовые срезы описывают локализацию в размеченных областях классов,
а не распознавание этих классов бинарным детектором.

При сопоставлении старого и нового отчёта необходимо одновременно фиксировать
домен (synthetic/real), режим, набор пар и фасадов, поддержку, правило
усреднения и калибровку. Расширение GeoSCD не должно менять собственные доступные
пары AnyChange. Глобальное пересечение со всеми методами может уменьшать
выборку; сравнение конкретной комбинации должно использовать своё пересечение.

Будущий TEST оценивается с заранее замороженными на VAL правилами и порогами.
Текущая LOFO-команда не подбирает параметры на TEST и не превращает расширение
выборки по GT в независимую случайную выборку фасадов.

## CPU-команды

Запускать из checkout с новой версией скриптов. Каталог `--metrics-run` — выход
`real_gt_metrics.py`, содержащий исходные GT и проверяемые карты; каталог уже
калиброванного LOFO-отчёта для этого аргумента не подходит.

```bash
FACADE_PY=/home/sasha/miniconda3/envs/scd_bench/bin/python
FACADE_RUNS=/home/sasha/Facade_Change_Benchmark/runs

nice -n 10 "$FACADE_PY" -u scripts/real_eval/real_final_fpr.py \
  --metrics-run "$FACADE_RUNS/2026-10-17-real-gt-geoscd297-001" \
  --budgets 0.01 0.05 0.10 \
  --out "$FACADE_RUNS/2026-10-18-real-final-fpr-001"
```

По умолчанию используются AnyChange/GeoSCD и все доступные scalar-методы:
одинаковые парные режимы либо PREVIOUS + HISTORY. Рабочая точка 10% добавлена
явно в этой команде, чтобы можно было проверить OR там, где исходная маска уже
превышает 5%. Она также не гарантирует достижимость каждого fold. Отбор методов
при необходимости: `--native-methods ...`, `--scalar-methods ...`.

Для первого разбора достаточно `summary.txt`, `comparisons.csv` и
`calibration_audit.csv`. Последний хранит для каждого fold достижимость бюджета,
порог, FPR калибровки и оставленного фасада. `coverage.csv` фиксирует исходное
покрытие. `class_comparisons.csv` сравнивает каждый AND/OR с обоими компонентами
по классам на одинаковых пригодных folds; соответствующие строки в
`class_macro.csv` имеют семейства `/matched_and` и `/matched_or`.
Подробные метрики, классовые срезы, рецепты и хеши находятся в том же
каталоге. Существующий выход не перезаписывается.

Пересборка ночного отчёта с OR и AND из уже сохранённых карт:

```bash
"$FACADE_PY" scripts/real_eval/real_temporal_night.py report \
  --run "$FACADE_RUNS/2026-10-17-night-run-001" \
  --out "$FACADE_RUNS/2026-10-18-night-report-or-001"
```

Команда может читать промежуточные сохранённые результаты; полнота видна в
`coverage.csv`. Модели не запускаются. Этот отчёт использует прежние пороги
synthetic VAL; отдельная команда выше выполняет новое real-VAL LOFO-сравнение.
При активном GPU-процессе для CPU-команд можно использовать отдельный worktree.
