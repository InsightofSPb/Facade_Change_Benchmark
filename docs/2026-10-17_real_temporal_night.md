# Реальные хронологии: широкий прогон готовых моделей

## Решение и научный смысл

Приоритет перед двумя докладами: широкий прогон существующих методов, затем
расширенная открытая семантическая сегментация (OVS), затем новые временные и
компрессионные модели и журнал для экспертов. Этот сценарий выполняет первый
этап. Модели не обучаются и веса не скачиваются.

Единица разнообразия — физический фасад. Начальная конфигурация: до 12 фасадов,
по одному кропу 512×512 в исходном масштабе, все пригодные даты выбранного вида.
Число фасадов — верхняя граница, а не обещание доступности геометрии и разметки.
Два кропа, 15–18 фасадов или более выбираются после замера времени. Больше кропов
одного здания не заменяет дополнительные независимые здания.

Фасады ранжируются по объединению пикселей с изменениями аннотированного набора
классов между соседними доступными датами. Пиксель в пространственном объединении
учитывается один раз, даже если повреждение появилось и затем было устранено.
Отдельно сохраняется сумма изменённых пиксельных наблюдений за все переходы.
Для здания с несколькими видами берётся максимальная площадь одного вида:
перекрывающиеся виды не складываются как независимые площади. Это пиксели
опорного снимка, не квадратные метры стены; разрешение снимка влияет на рейтинг.

Выбор чередует TEST → VAL → TRAIN; внутри split идут наиболее изменившиеся
фасады. Кропы ранжируются по такой же площади, требуют не менее 1024 известных
пикселей и 80% общей геометрической поддержки. Второй кроп одного вида должен
иметь IoU с первым не более 0.25. Известная область требует аннотаций обеих дат;
пустая маска не превращается в здоровый фон. Галерея показывает RGB, классы и
переходы, чтобы человек мог увидеть ошибки геометрии или аннотаций до inference.

Такой TEST заранее обогащён изменениями. Это диагностическая оценка выбранных
сложных случаев, не репрезентативная оценка полного TEST. По результатам нельзя
объявлять готовность ко всем фасадам города. TRAIN/VAL/TEST сохраняются отдельно,
также есть явно обозначенное объединение выбранных фасадов. Принадлежность
обучению MSDZip и головы semantic DINO проверяется по происхождению checkpoint;
непроверенная принадлежность остаётся unknown. Замороженный обычный DINO и
дообученная семантическая голова — разные случаи. Внешнее предобучение здесь
не аудируется.

## Режимы и сочетания

| Режим | RGB-сравнение | Оцениваемая цель |
|---|---|---|
| PREVIOUS | предыдущая доступная дата → текущая | изменение набора классов между этими датами |
| EARLIEST | первая доступная дата → текущая | отличие текущего состояния от первого |
| HISTORY | текущая дата против причинной памяти прошлых наблюдений | новое изменение относительно предыдущей доступной даты |

EARLIEST строит GT непосредственно из двух соответствующих масок. Объединение
всех соседних масок для него неверно: оно сохраняло бы уже устранённые изменения.
Пропущенные из-за отсутствующей геометрии даты явно перечисляются; «предыдущий»
означает предыдущий пригодный кадр, не обязательно соседний календарный год.

Парные режимы включают RGB-DIFF, SSIM, LPIPS, DINOv2, semantic DINO, AnyChange,
GeoSCD, MSDZip ABS и MSDZip MOD256. HISTORY использует существующее правило
TemporalMemory для DINOv2, semantic DINO, ABS, MOD256. Веса и правило не меняются.
При первом кадре память инициализируется; текущий кадр оценивается до обновления.
Порог обновления памяти остаётся исходным synthetic VAL H0 1%. Порог итоговой
маски — отдельный параметр. Память сериализуется вместе с результатом кадра;
продолжение проверяет причинную цепочку и хеши.

В отчёт также входят сочетания PREVIOUS-карты каждого из GeoSCD, AnyChange,
RGB-DIFF, SSIM, LPIPS с HISTORY-картой каждого доступного временного метода.
Операция AND оставляет область, подтверждённую обоими сигналами. Она может убрать
как ложные тревоги, так и истинные изменения, поэтому сравниваются P/R/F1/IoU/FPR,
а не одна площадь маски. Для каждой комбинации исходный метод пересчитывается
на тех же парах и пикселях. EARLIEST не умножается на карту нового события:
состояние и событие имеют разные цели.

## Команды на компьютере владельца

Работать в отдельном checkout, пока существующий GeoSCD завершает свою очередь:

```bash
cd /home/sasha/Facade_Change_Benchmark &&
git fetch origin &&
git worktree add --detach /home/sasha/Facade_Change_Benchmark_night origin/main &&
cd /home/sasha/Facade_Change_Benchmark_night

FACADE_PY=/home/sasha/miniconda3/envs/scd_bench/bin/python
FACADE_RUNS=/home/sasha/Facade_Change_Benchmark/runs
```

CPU-аудит не загружает модели и не растеризует GT. Он обнаруживает сохранённые
совмещения в runs, использует только совместимые завершённые артефакты, печатает
число фасадов с двумя и тремя пригодными датами по каждому split. Отсутствующие
совмещения не заменяются identity. Если TEST не покрыт геометрией, сначала нужен
отдельный alignment; данный сценарий его автоматически не выполняет.

```bash
"$FACADE_PY" -u scripts/real_eval/real_temporal_night.py audit \
  --run "$FACADE_RUNS/2026-10-14-temporal-experiment-002" \
  --snapshot "$FACADE_RUNS/2026-10-17-temporal-val-snapshot-001" \
  --runs-root "$FACADE_RUNS" \
  --splits test val train \
  --out "$FACADE_RUNS/2026-10-17-night-audit-001"
```

Выход: audit.json, facades.csv, alignment_coverage.csv, run.json. Для обсуждения
достаточно короткой консольной сводки. Явный список совмещений при необходимости
задаётся `--alignment-runs /path/run1 /path/run2`.

CPU-подготовка и просмотр:

```bash
nice -n 10 "$FACADE_PY" -u scripts/real_eval/real_temporal_night.py prepare \
  --audit "$FACADE_RUNS/2026-10-17-night-audit-001" \
  --max-facades 12 --crops-per-facade 1 \
  --out "$FACADE_RUNS/2026-10-17-night-prepared-001"

explorer.exe "$(wslpath -w "$FACADE_RUNS/2026-10-17-night-prepared-001/gallery.html")"
```

Подготовка читает доступные аннотации всей аудированной выборки для рейтинга,
затем сохраняет только выбранные полные истории. Оценка времени CPU пока не
подтверждена на машине владельца. Если выбор не подходит, можно создать другую
подготовку с явным `--buildings NAME1 NAME2` и новым каталогом. Исходная
галерея 13 PREVIOUS-пар остаётся отдельным экспериментом освещения; её пары
могут войти в новую выборку по общему правилу.

После освобождения GPU — реальный пилот. Он принудительно вычисляет выбранные
пары, а не выдаёт чтение кэша за скорость модели. По умолчанию: две пары каждого
парного режима и до трёх первых переходов одной истории на каждый HISTORY-метод.
История проходит все предыдущие кадры выбранного префикса.

```bash
"$FACADE_PY" -u scripts/real_eval/real_temporal_night.py pilot \
  --prepared "$FACADE_RUNS/2026-10-17-night-prepared-001" \
  --device cuda:0 --pilot-pairs 2 --pilot-history-frames 3 \
  --out "$FACADE_RUNS/2026-10-17-night-pilot-001" --detach

tail -f "$FACADE_RUNS/2026-10-17-night-pilot-001.log"
```

Инициализация и расчёт имеют сообщения каждые 15 секунд. При завершении — короткая
сводка score/init и timing.json. Диапазон — эвристика по измеренным вызовам,
не доверительный интервал. Он оценивает полный объём до переиспользования кэша.
Локальный лимит памяти в три образца на пиксель не означает максимум три вызова
на весь кадр: при неоднородной видимости может сохраниться больше старых RGB.

```bash
"$FACADE_PY" scripts/real_eval/real_temporal_night.py status \
  --run "$FACADE_RUNS/2026-10-17-night-pilot-001"
```

Очередь с мягким лимитом шесть часов и автоматическим CPU-отчётом:

```bash
"$FACADE_PY" -u scripts/real_eval/real_temporal_night.py run \
  --prepared "$FACADE_RUNS/2026-10-17-night-prepared-001" \
  --reuse-run "$FACADE_RUNS/2026-10-17-night-pilot-001" \
  --geoscd-run "$FACADE_RUNS/2026-10-17-geoscd-real-all-001" \
  --device cuda:0 --max-hours 6 \
  --out "$FACADE_RUNS/2026-10-17-night-run-001" --detach

tail -f "$FACADE_RUNS/2026-10-17-night-run-001.log"
```

Порядок: все методы PREVIOUS → все методы EARLIEST → доступные HISTORY-методы.
Готовые карты старого запуска, GeoSCD и пилота переиспользуются только при
совпадении RGB, поддержки и происхождения модели. История нового запуска
проигрывается причинно, её состояние сохраняется для дальнейшего resume.
Первая пара EARLIEST совпадает с первой PREVIOUS и в основной очереди
переиспользуется после той же проверки; pilot измеряет обе единицы независимо.

Лимит проверяется между единицами работы; начатая пара/кадр истории завершается,
затем сохраняется. Поэтому длительный вызов может выйти за шесть часов, а отчёт
добавит CPU-время. Лимит не обещает завершение всего плана. Если пилот не помещается,
сначала сокращают число кропов/фасадов или явно список методов, сохраняя общую
выборку для сравниваемых методов. Низкая занятость GPU не означает, что можно
безопасно запускать несколько тяжёлых работников одновременно.

Для продолжения повторить ту же команду с тем же каталогом и `--resume`.
Список методов, данные и код должны совпадать. Для повторения отказавших единиц
добавить `--retry-failed`; без него отказы остаются явно отмеченными. Новые веса,
другая выборка или другой код требуют нового запуска. Промежуточные таблицы можно
получить независимо от окончания GPU-очереди:

```bash
"$FACADE_PY" scripts/real_eval/real_temporal_night.py report \
  --run "$FACADE_RUNS/2026-10-17-night-run-001"
```

## Отчёт

Внутри `night-run-001/reports` сохраняются семь файлов: report.html, tables.csv,
per_facade.csv, per_class.csv, coverage.csv, comparisons.csv, provenance.json.
Карты и состояния лежат отдельно в служебных maps/units; картинки на каждый
метод не размножаются. HTML показывает три режима, split, покрытие и сравнения;
CSV содержит полные срезы.
В comparisons.csv общие дельты имеют region=overall, классовые — region=class;
обе стороны каждого сравнения используют одинаковые пары и поддержку.

Метрики — среднее по оцениваемым crop-frame наблюдениям внутри фасада, затем по
фасадам. P/R/F1/IoU используют наблюдения с положительной разметкой; FPR —
известные стабильные пиксели всех наблюдений. Счётчики — суммы пиксельных
наблюдений, не уникальная площадь стены. Классовые таблицы описывают локализацию
изменений в размеченных областях класса и направления gain/loss. Они не
превращают бинарный детектор в классификатор повреждений.

Данный отчёт использует замороженные пороги исходного synthetic VAL H0 отдельно
для каждого режима и рабочей точки 1%/5%. На реальных кадрах FPR может быть
намного выше. Это явная проверка переноса порогов. Ранее полученные real-LOFO
цифры с иной калибровкой нельзя непосредственно смешивать с этой таблицей.
Карты сохраняются непрерывными: отдельную калибровку по реальному VAL с фиксацией
порогов для TRAIN/TEST можно сделать затем на CPU без повторного inference;
на TEST пороги не подбираются. HISTORY-порог обновления памяти при этом не меняется.

Для первого доклада широкий прогон показывает поведение на реальных годах,
фасадах, типах размеченных изменений, перенос на новые здания и полезность
исторического сигнала как дополнения. Отдельный эксперимент на 13 парах с
экспозицией и тенью проверяет именно условия наблюдения: H0 — тот же снимок с
возмущением; H1 — реальная пара с возмущённым текущим снимком. Широкий прогон без
добавленных возмущений сам по себе не разделяет влияние освещения, геометрии и
физических изменений. Эти две части вместе поддерживают тему первого доклада.
Для второго доклада основа — PREVIOUS/EARLIEST/HISTORY, визуальные и компрессионные
оценки, сочетания и их измеренная стоимость. Улучшение конкретной модели является
результатом измерения, а не условием признания эксперимента полезным.

## Следующие параллельные задачи

1. **Расширенная OVS и семантическая ветвь.** Зафиксировать словарь городских
   объектов плюс наши повреждения, синонимы и соответствие каналам. Сначала
   сохранить вероятности/признаки и маски по каждому снимку независимо от CD.
   Сравнить существующую MaskCLIP-ветвь и выбранные открытые модели на одной
   онтологии; добавить «изменение есть, тип неизвестен». Для текстовых запросов
   проверить фактическую поддержку конкретной модели и адаптера. Не приписывать
   AnyChange/GeoSCD текстовый интерфейс без реализации. После этого сравнить
   два пути: семантика всей сцены → временное сравнение и CD-кандидаты →
   семантическое описание. Различать качество сегментации, локализации изменения
   и правильность типа повреждения. Расширенная городская онтология не меняет
   GT текущего damage benchmark автоматически.
2. **Признаки semantic DINO и неопределённость.** Сохранить признаки до
   семантической головы; сравнить обычный DINO, обученную голову по вероятностям,
   промежуточные признаки и их сочетания. Низкая уверенность должна выводиться
   отдельно; энтропия не является автоматически калиброванной вероятностью
   ошибки. Проверить правило воздержания, покрытие и потерю Recall. Заморозить
   настройки на TRAIN/VAL до TEST. Полезные результаты передаются в OVS и CD.
3. **Пространственная неожиданность вместо последовательности RGB-байтов.**
   Первый прототип: замороженная 2D-карта DINO-признаков и компактная модель
   нормального остатка/изменчивости на H0 TRAIN. Более простой базовый вариант —
   нормированный остаток признаков с оценкой масштаба по TRAIN; затем можно
   проверить небольшую свёрточную модель условного распределения. Сравнить с
   RGB ABS при равных фасадах, условиях и бюджете. Альтернативные VGG/ResNet/Swin
   — отдельные абляции после первого прототипа, не одновременный перебор всего.
   Прогнозируемая плотность в пространстве признаков — feature surprise, а не
   доказанная длина безошибочного RGB-кода. Если нужен компрессионный аргумент,
   отдельно определить квантование, вероятности и полную стоимость представления.
   RGB-ветку оставить контрольной: мелкие повреждения могут теряться в признаках.
4. **История и дополнение к базовым методам.** На готовых картах проверить AND
   для каждого базового метода; затем отдельно изучить мягкое взвешивание,
   неопределённость и критерий добавления наблюдения. Абляции: PREVIOUS, память
   без сброса, локальный сброс, число образцов, порог обновления. Проверить
   повреждение → ремонт → повторное повреждение. Не подбирать память по TEST.
   Новые правила требуют пересчёта причинной истории; простой новый порог
   визуализации карты — нет.
5. **Журнал для экспертов.** Прототип карточки события: фасад/вид/участок,
   даты до/после, RGB-кропы с контекстом, контур кандидата, предполагаемый тип,
   уверенность/причина воздержания, метод/пороги и ссылка на исходные файлы.
   Добавить действия «подтвердить», «отклонить», «уточнить класс», «плохое
   совмещение». Хранить машинное предложение отдельно от решения эксперта и
   историю правок; память модели и экспертный журнал — разные структуры.
   Для прототипа достаточно JSONL/SQLite и HTML; серверная БД не обязательна.
   Связь с прежними C,V следует закрепить по определениям статей, не объявлять
   автоматически, что нынешняя карта scores уже является тем же C или V.
6. **Дополнительные конкуренты.** После готовых таблиц восстановить RSCD,
   проверить Qwen-VL как семантическое описание/локализацию, отдельно измерить
   память, скорость, разрешение и причинный контекст истории. Обзор новых CD
   работ выполнять по первичным статьям и коду с датами; не называть новый
   метод SOTA лишь по году публикации. SAM3 рассматривать как отдельную
   семантическую ветвь/конкурента; замена backbone в авторском CD — отдельная
   модификация с собственной проверкой, не незаметное обновление baseline.

Эти задачи можно отдать разным агентам, но единый контракт должен задавать
идентификаторы фасадов/кадров, сетку и поддержку, онтологию, происхождение весов,
формат непрерывной карты и отказов. Общие GPU-запуски идут последовательной
очередью; независимые CPU-подготовка, интерфейс, анализ и тесты выполняются
параллельно. Каждый агент сдаёт код, небольшой воспроизводимый пример,
измеренное ограничение и конкретный формат артефактов.
