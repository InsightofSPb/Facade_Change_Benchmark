# Непрерывные семантические оценки и небольшая модель объединения

После жёсткого AND-пилота проверяем одну заранее фиксированную альтернативу:
сохраняется ли полезный сигнал до порогования DINO и можно ли использовать LPIPS
и MSDZip без обязательного последовательного отбрасывания событий. Это короткий
разведочный опыт на сохранённых картах, без нового inference, обучения DINO,
скачивания весов или поиска гиперпараметров.

## Два разных TRAIN

**DINO обучался на более широком семантическом наборе.** Четыре TRAIN-фасада
предыдущего временного пилота — это выбранные фасады с подготовленными временными
парами, а не полный набор обучения DINO. Одиночные семантические TRAIN-снимки сами
по себе не образуют временные пары. Новый скрипт не зашивает число четыре: он
использует все TRAIN-последовательности переданного prepared manifest, для которых
предусмотрен полный согласованный кэш. Состав сохраняется в `temporal_subset`.

Для расширения опыта нужен манифест дополнительных подтверждённых временных
последовательностей и соответствующие семантические/LPIPS/MSDZip карты. Новый
скрипт сам такие пары не создаёт. Он сохраняет доступные контракты и сведения
`training_exposure`, но не восстанавливает полный обучающий набор DINO из числа
временных фасадов.

TRAIN используется двумя способами:

- `train_fit`: модель объединения и порог подобраны на этих же TRAIN-фасадах.
  Это диагностика обучаемости, не независимая оценка.
- `train_fusion_oof`: каждый физический TRAIN-фасад целиком исключается из
  обучения модели объединения, нормализации признаков и калибровки порогов.
  Замороженные DINO/MSDZip могли обучаться на этом фасаде. Это проверка переноса
  **только новой модели объединения**, не независимость всей системы.
- `val` и `test`: одна модель, обученная на всех временных TRAIN-фасадах.
  TEST уже просматривался, поэтому остаётся разведочным; новую финальную
  независимую проверку этот опыт не создаёт.

## Зафиксированные варианты

| Имя | Оценка события |
| --- | --- |
| `semantic_delta` | gain = max(p1 − p0, 0), loss = max(p0 − p1, 0) |
| `lpips_only` | LPIPS, только бинарное изменение; класс/направление не предсказываются |
| `semantic` | логистическая модель от p_from, p_to |
| `semantic_lpips` | те же признаки и LPIPS |
| `semantic_lpips_msdzip` | те же признаки и MSDZip ABS |

Три обучаемые модели используют общие коэффициенты для всех классов и направлений,
а не отдельные параметры для редких событий. Для gain признаки равны p0,p1;
для loss они меняются местами. Скаляры LPIPS/MSDZip одинаковы для классов.
Никаких перемножений признаков, выбора классов или подбора регуляризации нет.

Признаки стандартизуются только на fitting TRAIN. Минимизируется взвешенная
бинарная кросс-энтропия плюс `0.5 * 0.01 * ||slopes||²`; intercept не штрафуется.
Используется детерминированный Newton solver на CPU с проверкой сходимости.
Для каждой пары берётся не более 8192 событий: до 4096 положительных и до 4096
отрицательных, seed 20261019 с идентификатором пары. Вес страты корректируется
по её полной численности, поэтому искусственное балансирование prevalence
не возникает. Сначала равные веса фасадов, затем пар внутри фасада, затем
классовых событий внутри пары. Нормализация и модель используют эти же веса.

Перед порогованием для каждого класса оставляется направление с большим logit;
при равенстве оба направления получают ноль. Разные классы могут пересекаться.
Бинарная оценка — максимум по классам и направлениям. Порог каждого из пяти
вариантов выбирается **на конечной бинарной оценке** по известным отрицательным
TRAIN-пикселям с целевым FPR 5%, равными весами фасадов и затем пар. Оператор
строгий `score > threshold`, ties сохраняются. На held-out фасадах измеряется
фактический FPR; соответствие 5% там не гарантируется.

Такой вариант может обнаружить изменение p0→p1 без пересечения порога состояния
0.5. В галерее старые S0/S1 показаны только для контекста, они не фильтруют события.
Полученные sigmoid scores не объявляются калиброванными вероятностями физических
событий. Исчезновение CRACK не означает ремонт. В этом опыте не утверждается точное
восстановление S1 через `(C,V)`; оценивается предсказание направленных событий.

## Поддержка, GT и метрики

Повторно используется проверенный read-only reader предыдущего пилота: идентичность
RGB, подготовленной геометрии, моделей, каналов, SHA-256 и кэшей проверяется до
обучения. Общая поддержка всех вариантов — геометрия ∩ LPIPS ∩ MSDZip. Пробелы
кэша останавливают весь опыт с `blocked`, без частичного сравнительного результата.

GT gain/loss выводится из состава аннотаций раннего и позднего кадра. Известны
только пиксели, имеющие аннотации обеих дат на общей поддержке. Неизвестные не
становятся отрицательными. Это изменение аннотаций, а не отдельная экспертная
разметка реальных физических событий. При inference GT и маска известной разметки
не участвуют; они используются для fitting и оценки.

Основные результаты: AP и бинарные/направленные Precision, Recall, F1, FPR.
Направленные TP/FP/FN объединяются по классам и направлениям **внутри пары**:
правильная локализация с неправильным направлением даёт FP и FN. Это не
class-macro. Отдельные строки `directed_class` показывают каждый класс/направление.

Все оценочные пиксели используются без семплирования. Пары усредняются внутри
фасада, затем фасады имеют равный вес. F1 основного протокола `all_frames`
сравнивается с тем же протоколом прошлого опыта. Альтернативный `positive_frames`
сохраняется отдельно. AP определяется только для пар с положительным GT, затем
усредняется по фасадам, где она определена; `ap_pairs`/`ap_facades` показывают
знаменатели. Пустые положительные наборы дают N/A, не 0 и не 1. Поэтому AP
не описывает поведение на полностью стабильных парах: для них нужен FPR.

## Локальный запуск

Все реальные NPZ остаются на компьютере владельца. Используются существующие
пути и среда; GPU не нужен. Время и пиковая RAM на реальных данных пока не измерены.
Все входные вероятности/карты удерживаются в памяти для повторного использования;
оценка AP сортирует полные векторы событий внутри каждой пары.

```bash
cd /home/sasha/Facade_Change_Benchmark

/home/sasha/miniconda3/envs/scd_bench/bin/python3.10 -u \
  -m scripts.real_eval.2026-10-19_continuous_semantic_updates \
  --semantic-run runs/2026-10-18-semantic-run-001 \
  --change-run runs/2026-10-18-night-run-001 \
  --out runs/2026-10-19-continuous-semantic-update-eval-001
```

Для проверки входов без fitting — `--audit-only` и другая новая output-директория.
Существующий output не перезаписывается. Требуются минимум два временных
TRAIN-фасада, отдельные VAL/TEST и положительные/отрицательные события в каждом
fitting-наборе. Фасад не может одновременно принадлежать разным split.

Результаты:

- `run.json`, `resolved_config.json`, `coverage.csv`: статус, полный состав
  временного поднабора, фиксированные настройки, контракты и хеши кода.
- `models/2026-10-19-*.json`: коэффициенты, нормализация, выборка с весами,
  fitting-фасады и пять порогов для каждого fold.
- `summary.csv`, `per_facade.csv`, `per_pair.csv`: оба протокола, четыре режима
  оценки, все варианты и направленные классовые результаты.
- `2026-10-19_report.html`, `2026-10-19_tables.md`, `gallery/`: таблицы и все
  TRAIN fusion-OOF / VAL / TEST пары. Цветные overlays показывают только бинарные
  TP/FP/FN; для верности класса/направления используются направленные метрики.
- `maps/`: конечные непрерывные бинарные scores, бинарные маски и bitsets gain/loss
  на общей поддержке для TRAIN fusion-OOF / VAL / TEST. Отдельные непрерывные
  классовые scores не дублируются; они восстанавливаются по модели и исходному кэшу.
- `2026-10-19_artifacts.json`, `2026-10-19_input_hashes.json`: связи с fold,
  пути и SHA-256 выходных моделей/карт и входных файлов.

Для первого разбора достаточно `summary.csv`, `per_facade.csv`, `models/`,
`resolved_config.json`, `run.json`. HTML передаётся вместе с `gallery/`.

## Проверка реализации

```bash
PYTHONPATH=tests python -m unittest \
  test_2026-10-19_continuous_semantic_updates \
  test_2026-10-19_semantic_updates \
  test_real_gt_calibration test_real_gt_metrics test_semantic_geometry -v
```

Проверяются исключение held-out фасада и VAL/TEST из fitting и калибровки,
поправка prevalence при семплировании, равные веса фасадов, постоянные признаки,
события без crossing 0.5, отсутствие GT в inference, временная обратимость,
ошибки направления, неизвестные пиксели, AP N/A, полный синтетический проход,
хеши неизменённых входов, отказ при пропущенном кэше и защита от перезаписи.
Это проверка кода, не результат на реальных фасадах.

Cloud 2026-10-19: в указанном запуске 42 проверки прошли; две существующие
проверки COCO-rasterizer из `test_real_gt_metrics` остановились на отсутствующем
`pycocotools`. Новый runner работает с готовыми NPZ и эту библиотеку не использует.
