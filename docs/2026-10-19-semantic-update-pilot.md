# Проверка направленных семантических обновлений на готовом кэше

Цель этого короткого опыта — проверить, умеет ли существующий DINO-сегментатор
указывать **где, какой класс и в каком направлении изменился**, и помогают ли
этому уже рассчитанные LPIPS и MSDZip ABS. Это эксперимент для решения о докладе,
а не проверка всего диссертационного положения и не доказательство новизны
представления `(C,V)`.

## Зафиксированный протокол

- Одна существующая DINO sigmoid-голова, порог состояния 0.5; никаких новых весов.
- Только PREVIOUS, та же подготовленная геометрия и исходные RGB.
- Каналы сопоставляются по имени с явным `category_to_channel`.
- Состояние — набор классов: пересечения сохраняются. Нулевое предсказание —
  отсутствие распознанного класса, а не утверждение «здоровый фасад».
- Три варианта: разность предсказанных состояний; разность AND LPIPS;
  разность AND LPIPS AND MSDZip ABS. Нового поиска комбинаций нет.
- Пороги LPIPS и MSDZip рассчитываются **по отдельности**, только на неизменных
  размеченных пикселях TRAIN, при FPR 5%. Сначала равные веса фасадов, затем кадров.
  Используется существующий строгий оператор `score > threshold` с учётом ties.
  Это FPR отдельных подтверждающих сигналов на TRAIN, не итоговой системы на VAL.
- Каждая композиция только отбрасывает семантические переходы. Она может повысить
  Precision, снизив Recall, но не добавить найденные сегментатором пропуски.
- Для всех трёх вариантов одинаковые пары и общая поддержка LPIPS/MSDZip/геометрии.
  Калибровка тоже использует эту поддержку. Оценка не ограничивается предсказанными ROI.
- Если хотя бы одной обязательной карты нет или её происхождение не совпало,
  опыт останавливается с `blocked` и `coverage.csv`. Новое inference не запускается,
  неполная выборка не превращается в итоговую сравнительную таблицу.
- TRAIN/VAL/TEST не смешиваются. Принадлежность здания нескольким split запрещена.
  TEST уже просмотрен в прошлой работе, поэтому здесь он — дополнительная
  разведочная проверка, а не нетронутый финальный holdout.

## Что именно предсказывается

Пусть `S0` и `S1` — битсеты предсказанных семантических состояний раннего и позднего
кадра. Для базового варианта `C = (S0 != S1)` на общей геометрической поддержке.
Варианты с подтверждением дополнительно пересекают C с бинарными сигналами.
`V = S1` в C; вне C значение V равно нулю и не используется.

Восстановленное принятое состояние: `S_accepted = where(C, V, S0)`.
У базового варианта оно совпадает с S1 внутри поддержки. У фильтрованных вариантов
оно сохраняет S0 там, где подтверждение отвергло переход. Нельзя объявлять это
точным восстановлением исходного S1 после фильтрации.

Для каждого класса вычисляются независимые `gain = ~S0 & S_accepted` и
`loss = S0 & ~S_accepted`. Исчезновение CRACK не означает появление REPAIRS.
Изменение текстуры внутри неизменного семантического класса не является таким
направленным обновлением; этот пилот его не описывает.

GT получается из изменения состава аннотаций, **не** из отдельной экспертной
разметки физического события. Известны только пиксели с ненулевым GT-битсетом
обеих дат на общей поддержке. Поэтому исчезновение последней аннотации в
неразмеченную область здесь не оценивается как подтверждённое исчезновение дефекта.

## Метрики и интерпретация

`binary_change` — обычная локализация C. `directed_events` — совместная оценка
троек «пиксель, класс, направление». Перед вычислением метрики суммируются
TP/FP/FN по всем классам и двум направлениям **внутри пары**; ошибка типа или
направления даёт FP и FN, даже если бинарная маска правильная. Это micro по событиям
внутри пары, затем macro по кадрам/фасадам; это не class-macro F1.
`directed_class` отдельно показывает каждый класс и направление на той же
полной известной области, включая ложные предсказания вне GT-области этого класса.

`exact_v_precision` — точность **полного нового набора классов** среди правильно
локализованных GT-изменений. Она условна и не штрафует ненайденные изменения.
Поэтому рядом приводится `exact_v_recall`: доля всех GT-изменённых пикселей, где
найдены C и полностью верное V; пропуски здесь дают нулевой вклад.

Основной протокол `all_frames`: среднее определённых метрик по парам одного
фасада, затем равное среднее по фасадам. Значение N/A не заменяется на 1.
В `summary.csv` также явно названный `positive_frames`, соответствующий старому
ночному отчёту: P/R/F1/IoU только на GT-положительных парах, FPR на всех парах
с отрицательными пикселями. Эти два протокола нельзя смешивать в одной дельте.
У `directed_events` FPR относится к отрицательным классовым событиям, а не к
бинарным неизменным пикселям; для оценки ложных областей используйте binary_change.

Исходные SHA-256, контракты моделей, конфигурация и статус сохраняются. Кэш
открывается только для чтения, повреждённые записи не перемещаются в quarantine.
Сохранённые сведения об обучении присутствуют в конфигурации, но новая проверка
полного training manifest здесь не выполняется. Отсутствие доказанного пересечения
не равнозначно доказанной независимости от обучения.

## Локальный запуск

Из checkout с этим изменением, в существующем `scd_bench`. Все пути ниже взяты
из переданного отчёта semantic-run; наличие NPZ на компьютере владельца проверит
сам скрипт. Загруженный в Cloud ZIP содержал таблицы, но не эти NPZ.

```bash
cd /home/sasha/Facade_Change_Benchmark

/home/sasha/miniconda3/envs/scd_bench/bin/python3.10 -u \
  -m scripts.real_eval.2026-10-19_semantic_updates \
  --semantic-run runs/2026-10-18-semantic-run-001 \
  --change-run runs/2026-10-18-night-run-001 \
  --out runs/2026-10-19-semantic-update-eval-001
```

Команда сама сначала проверяет весь нужный кэш, затем считает метрики. GPU не
нужен. Для одной проверки файлов можно добавить `--audit-only`, задав другую
новую выходную директорию. Повторный запуск в существующую директорию запрещён.
Время на реальных NPZ в Cloud не измерено; не следует обещать конкретные минуты.

Ожидаемые файлы:

- `run.json`, `resolved_config.json`, `coverage.csv` — статус, протокол и покрытие;
- `2026-10-19_thresholds.json` — пороги, TRAIN-фасады и пиксели калибровки;
- `summary.csv`, `per_facade.csv`, `per_pair.csv` — оба протокола усреднения,
  бинарные и настоящие направленные классовые метрики;
- `2026-10-19_tables.md`, `2026-10-19_report.html`, `gallery/` — таблица и **все**
  VAL/TEST-пары, включая неудачные, без отбора только красивых картинок;
- `maps/`, `2026-10-19_artifacts.json` — C, V, исходные предсказанные состояния
  и восстановленное принятое состояние с хешами;
- `2026-10-19_input_hashes.json` — использованные исходные файлы и SHA-256.

Для передачи таблиц достаточно ZIP выходной директории без `maps/`; HTML нужно
передавать вместе с `gallery/`. Если статус blocked — достаточно `run.json` и
`coverage.csv`, если последний успел появиться. Это повод исправить конкретный
путь/несоответствие, а не запустить весь benchmark заново.

## Проверка кода в Cloud

Датированное имя модуля с дефисами требует явного запуска unittest:

```bash
PYTHONPATH=tests python -m unittest test_semantic_updates -v
```

Проверяются неправильное направление при верном CD, многоклассовое восстановление
C,V, неизвестная разметка, FN после фильтрации, отсутствие влияния VAL/TEST на
калибровку, разные правила усреднения, несовпадающие модели, повреждённые/отсутствующие
карты, отсутствие перезаписи исходников. Сквозной синтетический пример намеренно
содержит улучшение от LPIPS и ухудшение от MSDZip: отчёт обязан показать оба.
Эти проверки не являются результатом на реальных фасадах.

Решение о докладе принимается после просмотра таблицы и фасадов: есть ли
воспроизводимый полезный результат с понятными ограничениями. Для утверждения
о пользе компрессионной оценки нужна наблюдаемая польза третьего варианта;
само присутствие MSDZip в схеме этого не доказывает. При провале опыт остаётся
диагностикой ограничений, без перебора новых настроек в оставшееся время.
