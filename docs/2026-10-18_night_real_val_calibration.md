# Ночной прогон: CPU-калибровка по реальному VAL

## Вопрос и данные

Дают ли готовые карты методов полезное дополнение друг к другу при ограничении
**итогового FPR**? Отдельно сравниваются готовые PREVIOUS и HISTORY одного
метода. Основное сравнение — F1 вместе с фактическим FPR и покрытием;
Precision, Recall, IoU и классовые срезы служат дополнительными показателями.

Команда `real_temporal_night.py calibrate` читает `run.json`, `units/*.json`,
готовые NPZ-карты и подготовленные RGB/аннотации. Она не запускает модели,
не обучает, не меняет исходный прогон и не пересчитывает память.
Файлы TRAIN/TEST не декодируются. EARLIEST не включён: у него другая цель.

Состав определяется манифестом. При девяти PREVIOUS-методах и трёх HISTORY
получаются 12 одиночных каналов и 66 неупорядоченных пар, каждая с AND и OR.
Это scalar/scalar, native/scalar, native/native внутри PREVIOUS, внутри HISTORY
и между режимами. MOD256 HISTORY не появляется, если его нет в прогоне.
Отсутствующие карты не вычисляются заново.

## Протокол

Единица исключения и усреднения — физический фасад `building_id`. Для каждого
оставленного VAL-фасада используются только отрицательные GT-пиксели остальных
VAL-фасадов. При пяти фасадах это пять folds «4 → 1». Фасады имеют равный вес;
внутри фасада равный вес имеют наблюдения с известными отрицательными пикселями,
внутри наблюдения — эти пиксели. Положительные примеры не выбирают пороги.
Без отрицательных пикселей у других фасадов fold помечается `unsupported`.

Каждая пара методов использует своё пересечение доступных наблюдений и
известной геометрически допустимой поддержки. Оба компонента самостоятельно
калибруются и оцениваются на этом же пересечении. Сравнение сочетания с каждым
компонентом повторно агрегирует только folds, где доступны обе стороны.
Глобальное пересечение всех методов не сокращает выборку одиночного метода.

Для scalar/scalar строятся взвешенные эмпирические ранги отрицательных примеров
на калибровочных фасадах: `r_m(s) = sum_i w_i * [s_m,i < s]`, `sum_i w_i = 1`.
Итоговые карты: `min(r_left, r_right)` для AND и `max(...)` для OR.
Для каждой операции независимо выбирается наименее строгий порог `q > t`,
при котором итоговый взвешенный FPR не превышает бюджета. Это заранее заданное
симметричное семейство правил, а не поиск всех двухпороговых решений по
положительной разметке. Равные оценки не разделяются. Оценки выше максимума
калибровки сохраняют возможность срабатывания. Аудит содержит эквивалентные
сырые пороги обеих ветвей; `predict_choice` воспроизводит маску по JSON-рецепту.

Для native/scalar используются исходная бинарная маска и порог scalar-карты;
калибруется итоговый AND/OR. Если FPR native выше бюджета, OR недостижим:
он не получает фиктивную пустую маску. Если AND удовлетворяет бюджету с полностью
открытой scalar-ветвью, сохраняется режим `all`, включая положительные пиксели
с низкой оценкой. Одиночные native и native/native фиксированы; их маски
сохраняются, превышение бюджета отмечается `fixed_reference_outside_budget`.

Целевые 1%/5% ограничивают калибровочные фасады; фактический FPR оставленного
фасада может быть выше. Достигнутые значения различаются также из-за связанных
оценок. Одинаковый бюджет не означает одинаковый фактический FPR.

Память HISTORY отражает исходные synthetic-пороги обновления. Меняется только
порог отображения готовой карты в бинарную маску. PREVIOUS → HISTORY здесь —
сравнение двух готовых режимов с реальной калибровкой выходной маски,
а не чистая абляция правила обновления памяти.

## Локальный запуск

Из checkout с новой версией кода, в работающем Python-окружении проекта:

```bash
python -u scripts/real_eval/real_temporal_night.py calibrate \
  --run /home/sasha/Facade_Change_Benchmark/runs/2026-10-18-night-run-001 \
  --out /home/sasha/Facade_Change_Benchmark/runs/2026-10-18-night-real-val-lofo-001 \
  --budgets 0.01 0.05
```

После прерывания — та же команда с `--resume`. Готовые семейства сохраняются
атомарно с отдельной квитанцией хеша. Продолжение проверяет исходные файлы,
настройки, код и готовые семейства. Изменённые данные или код требуют нового
каталога. Незавершённое семейство пересчитывается; завершённые переиспользуются.
В конце проверяется неизменность входов за время работы. `provenance.json`
является маркером законченного отчёта.

`--methods rgb_diff ssim anychange msdzip_abs` задаёт меньшую матрицу для отдельного
каталога: все доступные PREVIOUS/HISTORY выбранных методов. Полный запуск не
требует этой опции. Время зависит от числа известных пикселей и чтения NPZ;
синтетическая проверка не оценивает время реального прогона. Кэш известных
пикселей в RAM растёт пропорционально числу пикселей и каналов.

## Выходные файлы

| Файл | Содержимое |
|---|---|
| `summary.txt`, `report.html` | Сводка, одиночные методы и сопоставления |
| `tables.csv`, `per_facade.csv`, `per_pair.csv` | Общие метрики, каждый фасад и наблюдение |
| `comparisons.csv`, `comparison_per_facade.csv` | Сочетание против каждой базы; PREVIOUS → HISTORY; общий и классовые срезы |
| `per_class.csv`, `per_class_facade.csv` | Локализация в аннотированных классах, change/gain/loss |
| `calibration_audit.csv` | Каждый fold: фасады калибровки, пороги, достижимость, калибровочный и фактический FPR |
| `coverage.csv`, `input_coverage.csv` | Покрытие рабочих точек; исходные отказы, пропуски, пустая известная область по фасадам |
| `timing.csv` | Измеренное время успешного нового инференса VAL, отдельно от переиспользованных карт |
| `cpu_timing.csv` | Время CPU-расчёта каждого семейства |
| `run.json`, `provenance.json`, `families/` | Контракт, версии/хеши, источники, завершение и возобновляемые результаты |

Метрики — доли. P/R/F1/IoU усредняются по положительным кадрам, затем фасадам;
FPR — по кадрам с известными отрицательными пикселями, затем фасадам. Суммарные
confusion counts служат аудиту и не определяют macro-F1. Сопоставления показывают
число фасадов с ростом, падением и равенством F1.

Время инференса не подменяется чтением кэша: у прежних карт исходная длительность
может быть неизвестна. В HISTORY отдельно учитываются длительность единицы и
вызовы scorer. Это не полное GPU-время прошлых попыток, не end-to-end время
сочетания и не новый замер.

## Границы выводов

Это разведочная LOFO-калибровка на выбранном, обогащённом изменениями VAL.
Множество сочетаний не создаёт независимый TEST. Неизвестная принадлежность
фасада обучению semantic DINO остаётся `unknown`; исключение из калибровки
не устраняет ограничения происхождения модели. Классовый срез описывает
локализацию внутри аннотированного класса; бинарный детектор не предсказывает
класс. Статистическая значимость не рассчитывается.

После разбора отчёта фиксируем короткий список правил и пороги для отдельной
проверки 13 пар с освещением. Этот CPU-запуск их не включает.
