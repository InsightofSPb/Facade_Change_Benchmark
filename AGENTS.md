# Работа над Facade Change Benchmark

Отвечай владельцу по-русски. Сначала прочитай README.md, затем документ по текущей задаче.
Codex Cloud редактирует этот репозиторий и выполняет CPU-проверки. Пути `/home/sasha/...`
в конфигурации относятся к компьютеру владельца. Их отсутствие в Cloud ожидаемо.

## Рабочий цикл

1. Посмотри `git status`; сохраняй чужие изменения.
2. Уточни существующий код и контракт, прежде чем добавлять новый скрипт.
3. Проверь изменённую часть и сквозной синтетический пример. Основная команда:
   `python -m unittest discover -s tests -v`.
4. В Cloud зависимости устанавливаются `bash scripts/setup_cloud.sh`. Локально сначала
   проверь существующие `lposs`/`scd_bench` командой `python -B scripts/audit_environment.py
   --run-tests --out runs/env-001`. До разбора аудита не создавай новую среду и не обновляй пакеты.
5. Для локальной проверки на реальных данных дай точную команду и список ожидаемых
   файлов. Сравни результаты, когда владелец их передаст.
6. Укажи выполненные команды, результаты, ограничения и следующий конкретный шаг.
   Обновляй датированные документы, когда меняются решения или научная интерпретация.

## Контракт исследования

- Исходный сигнал — RGB uint8 на исходной решётке, без автоматического EXIF-поворота.
  Гомография оценивается на уменьшенных grayscale proxy, итоговые RGB выводятся
  из оригиналов. Семантическая сегментация — отдельная ветвь.
- `source_to_reference` означает направление геометрии. В текущей команде reference
  — более раннее наблюдение, source — более позднее. Это не утверждение о здоровье опоры.
- Масштаб опорных пикселей сохраняется; холст расширяется по объединению наблюдений.
  Огромная/вырожденная H вызывает отказ, а не скрытое уменьшение изображения.
- Поддержка вычисляется из геометрии, границ интерполяции и alpha. Чёрный RGB может
  быть валиден. `overlap` не является маской окклюзий деревьями/машинами/лесами.
- Научная единица — физический фасад/здание. `view_id` — конкретный вид; `building_id`
  объединяет виды одного здания. До подтверждения building_id не создавай train/test.
  Не дели случайно коррелированные кропы и виды между train/val/test.
- Имя файла даёт гипотезу о годе/виде; `metadata_review.csv` фиксирует ручное подтверждение.
  Не удаляй неизвестные записи из общего манифеста.
- Не называй семантическую маску повреждений на одном снимке истинной разметкой
  временного изменения. RGB-разность и inliers не доказывают обнаружение дефектов.
- Для будущего обучения: только прошлая история; ремонт начинает новый локальный
  эпизод. Повторное повреждение того же места сохраняется как отдельное событие.
- Все запуски — в новой директории с run.json, конфигурацией, хешами и конечным статусом.
  Не затирай результаты повторного запуска, не придумывай прошлые эксперименты.
- Реальные данные, веса, локальные пути и outputs не добавляются в Git. Не запускай
  полное обучение/benchmark и не скачивай веса в рамках небольшого исправления кода.
- При использовании GPU проверь память и процессы; чужие задачи не останавливай.
  LoFTR и другие модели загружай последовательно, фиксируй версии и хеши весов.
- Исходные репозитории владельца — справочные источники, не цели удаления/очистки.

## Структура

`data.py` отвечает за COCO и пути; `geometry.py` — за координаты и поддержку;
`alignment.py` — за взаимозаменяемые сопоставители и общий MAGSAC;
`pipeline.py` — за один запуск и его отчёт. Не добавляй общий framework ради одного метода.
Контрольные синтетические примеры находятся в `demo.py` и `tests/`, реальные результаты — в `runs/`.

LoFTR-адаптер в начальной версии ещё не проверен с реальным checkpoint.
Не записывай его как проверенный метод без отдельного успешного запуска и осмотра результата.
